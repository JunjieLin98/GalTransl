## 1. 项目概述

### 1.1 定位

galTrans 是一个面向社区开源的 Galgame 汉化桌面套件:用户拖入游戏目录,软件自动识别引擎、解包、提取文本,接入 LLM API 完成翻译,最终回封产出可分发的中文汉化补丁。

### 1.2 与上游的关系

本项目 **fork GalTransl(GPL-3.0)**,复用其成熟的 LLM 翻译核心(词典、缓存、反思校对、并发、插件系统、Tauri+React GUI),补齐上游缺失的两块:

1. **流水线编排层**:引擎识别 → 解包 → 提取 → 翻译 → 注入 → 打包的全自动串联(上游只管 JSON→JSON 翻译段,前后处理全靠用户手拼外部工具);
2. **补丁工作台 GUI**:把上述流程做成向导式桌面体验,解决上游最集中的"上手门槛高、流程黑盒"痛点。

### 1.3 目标

- G1:Kirikiri 系游戏从"拖入目录"到"产出补丁"全程 GUI 可完成,无需命令行;
- G2:翻译质量不低于上游 GalTransl 直接使用(复用其词典/反思/找错机制,不劣化);
- G3:任何步骤失败时,用户看到的是"人话 + 可行动指引",而非堆栈;
- G4:新引擎接入 = 新增一个声明式 profile,不改核心代码;
- G5:诚实的能力边界——引擎支持程度分级公示,不承诺做不到的事。

### 1.4 非目标(明确不做)

- 实时 hook 翻译(LunaTranslator/XUnity.AutoTranslator 定位,Unity 场景仅作 fallback 引导);
- 图片内文字 OCR;
- 封包解密服务(KrkrExtract/xp3-brute 等解密工具不由本项目分发,用户自备);
- 无人工审校的全自动补丁发布(合规红线,见 §7);
- Il2Cpp 游戏的离线回封(引导走 XUAT 外挂文本方案)。

## 2. 术语表

| 术语 | 含义 |
|---|---|
| Galgame / 视觉小说 | 以对话文本为主的日式游戏 |
| 引擎 | 游戏的底层框架(Kirikiri、Unity、Ren'Py 等),决定封包与脚本格式 |
| 封包 | 游戏资源打包格式(如 .xp3);解包 = 还原为散文件 |
| 提取 / 导入 | 从脚本导出文本为中间格式 / 将译文写回脚本 |
| 回封 / 免封包 | 重新打包封包 / 让游戏直接读散装补丁文件 |
| name-message JSON | GalTransl 中间格式:`[{"name":"咲來","message":"…"}]`,有 name 即对话 |
| EngineProfile | 声明式引擎适配 YAML(本项目的核心扩展机制) |
| 能力等级 L1–L4 | 引擎自动化程度分级,见 §5.2 |
| patch.xp3 | Kirikiri 游戏原生加载的补丁封包;已存在时递增为 patch2.xp3 |
| version.dll | KirikiriUnencryptedArchive 免封包方案所需的代理 DLL |
| TEaR | Translate→Estimate→Refine 翻译质量闭环范式(实验特性) |

## 3. 用户画像

### P1 汉化组熟练者
- 熟悉解包/注入基本概念,可能用过 GARBro、Translator++、GalTransl CLI;
- 诉求:省掉手工拼工具链的时间;批量、可重跑、缓存可控;对 AI 翻译结果会人工精修;
- 失败时愿意读文档、看日志。

### P2 社区新手(主要服务对象,也是上游流失最严重的群体)
- 只想"让游戏变中文",不了解引擎/封包/编码概念;
- 诉求:拖入游戏目录 → 下一步 → 下一步 → 拿到补丁;
- 遇到堆栈式报错即放弃(上游 issue 区大量此类求助);
- 需要被明确告知:哪些游戏能全自动、哪些只能半自动、缺字怎么办。

## 4. 用户旅程

### J1 首次启动
启动桌面端 → 首启向导(选择界面语言 → 配置 API:key/endpoint/模型 → **连接自检**(发起一次真实小请求,验证 key/网络/模型可用)→ 完成提示)。API key 经 Windows DPAPI 加密存储。

### J2 端到端打补丁(主旅程)
1. 拖入游戏目录 → 自动引擎检测,展示识别结果与**能力等级(L1–L4)**及等级含义;
2. 确认提取范围(可勾选脚本文件)→ 提取,展示统计(行数/对话数/人名数/预估 Token 量);
3. (可选)术语表生成向导:抽取高频专有名词 → 生成 GPT 字典草稿 → 用户确认;
4. 翻译:实时进度(文件级/总进度/Token 消耗/ETA),可暂停/取消/续翻;
5. 查看只读问题列表(残留日文/超长/字典未命中等,按类型筛选跳转);
6. 注入 → 打包 → 在 `dist/` 产出补丁(patch.xp3 + version.dll(按需)+ TRANSLATION_NOTICE + 安装说明)。

### J3 失败与恢复
任一步失败 → 展示**错误码 + 人话解释 + 可行动指引**(如加密 xp3 → 指引用户自备解密工具并放置密钥);修复后可**从任意已完成步骤继续**,无需从头再来;翻译段天然有上游缓存兜底(断点续翻)。

### J4 人工精修(v1.0)
双语对照编辑器 → 按问题类型筛选 → 修改译文(写回经缓存条目 + 人工锁定位)→ 输出自动重建;被锁定行不再被增量重翻覆盖。

## 5. 功能需求

> 分级:**A = CLI alpha(M1 末)**;**B = v0.1(M2 末)**;**C = v1.0**。共 36 项具体需求;A/B/C 级 34 项每条含验收标准(AC),H 级 2 项为实验特性(不设 AC,不入版本验收)。

### 5.1 FR-A 引擎检测与适配

| ID | 需求 | 级别 | 验收标准 |
|---|---|---|---|
| FR-A1 | 引擎自动检测:基于特征规则(封包后缀、特征文件),输出引擎名 + 置信度 | A | 样例库(krkrz 自建样例 + ≥1 真实游戏)检出率 100%,误报为 0 时才通过 |
| FR-A2 | EngineProfile 声明式注册,新增引擎不改核心代码 | A | kirikiri.yaml 完整驱动端到端;新增一个仅含 YAML 的 profile 可被加载 |
| FR-A3 | 检测结果展示能力等级 L1–L4 及其含义 | B | GUI 检测页对每级有明确文字说明 |
| FR-A4 | per-game 覆盖:用户可对任意 profile 字段按游戏覆盖 | B | 覆盖项持久化于 PatchProject,重跑生效 |
| FR-A5 | Unity 检测(Mono/TextAsset 类;Il2Cpp 识别后引导 XUAT) | C | Unity 样例检出;Il2Cpp 样例给出引导文案 |

### 5.2 FR-B 能力分级(四级兜底矩阵)

| 等级 | 含义 | 自动化范围 |
|---|---|---|
| L1 全自动 | 专用工具具备提取+导入(如 msg-tool 的 Kirikiri .ks/.scn) | 完整流水线 |
| L2 全自动(受限) | SExtractor 专用预设或 BIN 暴力正则的提取+导入回填(受导入编码限制) | 完整流水线,失败明确降级 |
| L3 半自动 | 仅能提取(SExtractor/用户手动)→ 翻译产出 | 到翻译产出为止,回封人工 |
| L4 仅翻译 | 用户自备 JSON 直接接入 | 仅翻译 |

| ID | 需求 | 级别 | 验收标准 |
|---|---|---|---|
| FR-B1 | profile 声明 capability,L2 导入失败时明确降级提示并产出 L3 产物 | B | 构造一个导入失败用例,验证降级文案与产物 |
| FR-B2 | 产品文案不得承诺超出等级的能力 | B | 评审 checklist |
